# Misa IT preparation and first sessions

This is a proposed learning plan for discussion, not a Misa IT curriculum or confirmed placement agreement. The official [Misa IT page](https://www.misa.se/kontakt/misait) describes Python and game-development learning and individual support. Playwright/JavaScript mentorship should be confirmed locally. Source checked: 2026-09-20.

## Bring to the first discussion

- Repository README and the 16-week plan.
- One risk you can explain, one test case, and an honest statement of current progress.
- A proposed weekly capacity and one preferred way to receive feedback.
- A short list of tools you need: your GitHub account, a supported browser, and later Node.js/Playwright.

Keep personal support needs and individual agreements in private notes, outside the public repository.

## Questions to resolve together

1. Can this QA project be part of my individual plan, and who can review one artifact or PR each week?
2. Is JavaScript/Playwright support available? If not, can I continue independently and seek review of testing reasoning, or agree a smaller Python/API project later?
3. May I use my own laptop and GitHub account, and install the required development tools?
4. What weekly workload, session length, and feedback format are realistic?
5. When would a practice placement be appropriate, and who coordinates employer contact? Use “LIA” only if an education provider confirms that arrangement.

## First three work sessions

| Session | Time box | Concrete output | Stop condition |
| --- | --- | --- | --- |
| 1 | 45–60 min | Walk through login → cart → checkout; note expected behavior and questions | One journey understood, uncertain expectations listed |
| 2 | 45–60 min | Review R-01 and R-05; execute TC-AUTH-001 and TC-CHK-002 in clean sessions | Two dated results with actual observations and evidence, or a documented blocker |
| 3 | 30–45 min | One small PR containing the two records and one learning note | Self-review complete; one specific feedback request |

These sessions begin Week 1; they do not satisfy every Week 1 criterion. If time runs out, record the next smallest action instead of expanding the task.

## Adapt the pace

The existing 12-hour weekly estimate is a starting assumption. At lower capacity, split each week into multiple work blocks. Retain evidence and review time; defer extra browsers, TypeScript, and additional tooling first. Limit work in progress to one issue. End a session with: what changed, evidence, blocker, next action.

## Five-minute demonstration

1. Explain the customer risk (30 seconds).
2. Show the related case and its expectation (60 seconds).
3. Show an actual result and evidence, or clearly show a template if nothing has run (90 seconds).
4. Explain one limitation and the next test (60 seconds).
5. Ask for feedback on one decision (60 seconds).
